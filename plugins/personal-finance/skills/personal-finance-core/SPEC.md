# 사회 초년생 자산관리 공통 명세

이 문서는 범용 온보딩 스킬과 개인용 지속 관리 스킬이 공유하는 계약입니다. 저장소 제품과 실행
환경에 관계없이 같은 회계 결과를 만들어야 합니다.

## 권한과 보안

- 스킬은 송금, 납부, 상품 가입, 투자 주문, 계좌·카드 해지를 실행하지 않습니다.
- 사용자가 실제로 수행했다고 확인한 금융 행위만 원장에 반영합니다.
- 전체 계좌번호, 전체 카드번호, 비밀번호, CVC, OTP, 로그인 정보를 묻거나 저장하지 않습니다.
- 계좌와 카드는 사용자가 알아볼 수 있는 별칭으로 식별합니다.
- API 키와 인증 토큰은 인계 데이터와 원장에 넣지 않고 실행 환경의 secret store에서 관리합니다.
- 자동 추출 결과는 `verification_status=pending`으로 등록하며 확인 전에는 파생 합계에 반영하지 않습니다.

## 책임 경계

범용 온보딩 스킬은 사회 초년생의 기준시점 상태, 관리 원칙, 실행 설정을 확인하고
`schema_version=1.0.0`인 인계 데이터를 만듭니다. 개인용 지속 관리 스킬은 인계 데이터를 검증한
뒤 원장 이벤트, 결산, 정정, 알림 상태를 관리합니다.

Outline, Notion, 로컬 Markdown은 교체 가능한 저장소 어댑터입니다. 공통 원장과 인계 데이터는
특정 저장소의 문서 구조나 API 필드에 의존하지 않습니다.

## 잔액 차원

계좌는 `cash_like`와 `liquidity`를 가지며, 계좌 안의 금액은 겹치지 않는 position으로 나눕니다.
position은 `available`, `allocated`, `restricted` 중 하나의 정책 상태를 가집니다.

| 파생 값 | 계산 |
| --- | --- |
| 총자산 | 모든 position 금액의 합 |
| 현금성 자산 | `cash_like=true` 계좌에 속한 position의 합 |
| 즉시 유동 자금 | `liquidity=immediate` 계좌에 속한 position의 합 |
| 정책상 사용 가능액 | `liquidity=immediate`이면서 `policy=available`인 position의 합 |
| 목적성 자금 | `policy=allocated`인 position의 합 |
| 정책상 제한 자금 | `policy=restricted`인 position의 합 |
| 유동성 제한 자금 | `liquidity`가 `restricted` 또는 `illiquid`인 position의 합 |
| 순자산 | 총자산에서 원금, 미지급 이자, 미지급 수수료를 포함한 총부채를 뺀 값 |

각 파생 값은 서로 다른 질문에 답합니다. 목적성 자금과 유동성 제한 자금이 겹칠 수 있으므로 둘을
더한 뒤 총자산에서 빼지 않습니다.

| 목적성 자금 배정 | 총액 불변, 정책상 사용 가능액 감소 | 불변 | 없음 | 없음 |

이자와 수수료는 `finance_charge`에서 지출과 부채로 인식합니다. `debt_payment`는 이미 인식된
원금, 이자, 수수료를 상환하므로 지출을 다시 만들지 않습니다.

환불의 예산 귀속은 `budget_policy.refund_period_policy`로 정합니다. `receipt`는 환불받은 기간에
음의 지출로 표시하고 `source`는 원거래 기간을 수정합니다. 두 정책 모두 환불을 별도 수입으로
기록하지 않으며 원거래 링크를 보존합니다.

## 이벤트 모델

이벤트는 하나의 선형 상태를 사용하지 않습니다.

| 축 | 값 |
| --- | --- |
| 거래 유형 | 구매, 이체, 배정, 납부, 환불, 포인트, 의무 등 실제 사건 |
| 회계 인식 | `not_applicable`, `planned`, `conditional`, `recognized`, `reversal` |
| 결제·상환 상태 | `not_applicable`, `unsettled`, `partially_settled`, `settled` |
| 검증 상태 | `pending`, `confirmed`, `rejected` |

축이 적용되지 않는 이벤트는 `not_applicable`을 사용합니다. 파생 합계에는 `confirmed` 이벤트만
반영합니다.

실제 자산·부채 사건은 `recognized`, 환불과 취소는 `reversal`, 계획·예약·확정 약정은 `planned`,
조건부 약정은 `conditional`, 포인트 적립·사용·소멸은 `not_applicable`만 허용합니다. 카드·할부 구매,
대출 실행과 금융 비용은 `unsettled`, 카드·부채 상환은 `partially_settled` 또는 `settled`이며, 나머지
이벤트의 결제·상환 상태는 `not_applicable`입니다.

계좌 이체는 출금과 입금 leg를 함께 변경하는 하나의 원자 이벤트입니다. 목적성 자금 배정은 별도
원자 이벤트입니다. 같은 사용자 행동에서 발생한 이벤트는 `event_group_id`로 묶되 개별 정정과
취소가 가능해야 합니다.

`account_transfer`는 서로 다른 실제 계좌의 position 사이에서 policy와 `allocation_id`를 그대로
보존합니다. 같은 계좌 안에서 available 자금을 allocated 또는 restricted 상태로 바꾸는 동작은
`fund_allocation`만 사용합니다.

정정은 원본을 수정하지 않습니다. 새 이벤트가 `supersedes_event_id`로 원본을 대체합니다. 승인
취소와 일반 취소는 `cancels_event_id`로 원본을 비활성화합니다. 파생 상태는 활성 이벤트만 다시
재생해 계산합니다.

관계 이벤트가 취소되거나 대체되면 그 이벤트의 취소·대체 관계도 적용하지 않습니다. 모든 관계
이벤트의 active 여부를 먼저 계산한 뒤 active 관계만 대상에 적용하며, 관계 cycle은 거부합니다.
자동 추출 `pending` 이벤트를 확인할 때는 같은 source identity를 가진 새 `confirmed` 이벤트가
`supersedes_event_id`로 pending 원본을 대체합니다. 원본은 수정하지 않고 재시도는 멱등 처리합니다.
`pending`과 `rejected` 이벤트의 관계는 파생 상태와 관계 그래프에 적용하지 않습니다. 새 확정 이벤트는
append 전에 기존 이벤트와 함께 임시 replay하여 관계 cycle, 참조, 잔액 무결성을 확인합니다.

`cancels_event_id`는 이벤트 top-level 필드만 사용합니다. payload에 같은 이름을 넣지 않습니다.
환불은 `confirmed`이며 현재 active인 현금·카드·할부 구매만 원본으로 참조할 수 있습니다.

API처럼 고유 원본 ID가 있는 입력은 `source.kind`, `source.system`, `source.external_id` 조합으로
멱등 처리하며 `external_id`가 있으면 비어 있지 않은 `system`이 필수입니다. 수동 입력과 OCR의
fingerprint는 중복 후보 탐지에만 사용합니다. 후보가 있으면
사용자 확인 전까지 새 이벤트를 확정하지 않습니다.

| 단순 계획 | 가능 | 없음 | 없음 | 없음 |
| 취소 가능한 예약 | 가능 | 없음 | 없음 | 없음 |
| 취소 비용이 있는 예약 | 가능 | 없음 | 없음 | 조건과 최대 노출액 |

## 포인트 기본 정책

기본 정책은 소비가치 회계가 아닌 현금 중심 회계입니다.

- 포인트 적립과 소멸은 참고 잔액만 바꿉니다.
- 포인트 사용은 참고 잔액을 줄이고 실제 현금·카드 결제액만 지출로 기록합니다.
- 포인트 현금화는 현금과 기타수입을 늘립니다.
- 계좌에 직접 입금된 캐시백은 현금과 기타수입을 늘립니다.
- 즉시 할인과 쿠폰은 실제 결제액을 줄입니다.
- 환불과 승인 취소는 원거래 반대 효과이며 캐시백으로 분류하지 않습니다.

## 온보딩 정보 등급

| 등급 | 의미 | 완료 조건 |
| --- | --- | --- |
| 차단 필수 | 현재 자산, 부채, 지급 가능성을 계산하는 데 필요 | 정확한 값이나 계산 가능한 현재 상태 확인 |
| 확인된 미정 | 미청구·변동값처럼 현재 정확한 값이 없는 이유를 확인 | 값 성격, 상한·추정 근거, 다음 확인 시점 기록 |
| 후속 확인 | 시작 상태를 왜곡하지 않고 운영 중 확인 가능 | 인계 데이터의 follow-up으로 보존 |

모든 초기 잔액과 의무에는 snapshot 기준일시와 개별 `observed_at`을 기록합니다. 값은 `exact`,
`estimated`, `upper_bound`, `variable`, `unbilled` 중 하나이며, `exact`가 아니면 `next_review_at`이
필수입니다.

표준 차단 항목 ID는 `snapshot`, `accounts_and_positions`, `liabilities`, `next_income`,
`essential_obligations`, `payment_capacity`입니다. 각 항목은 `blocking`이면서 `complete`여야 합니다.
모든 계좌에는 잔액이 0원이더라도 opening position이 하나 이상 있어야 합니다.

검증된 handoff는 `handoffToOpening`에서 measured money를 숫자형 opening으로 한 번 변환한 뒤 원장에
전달합니다. raw opening의 모든 부채는 `principal`, `accrued_interest`, `fees_due`를 숫자로 명시하며
누락값을 0으로 간주하지 않습니다.

인계 데이터의 `cashflow_horizon`은 다음 수입의 금액·예정일, 다음 수입 전 필수 의무의 금액·지급일·
지급 계좌, 정책상 사용 가능액과 지급 가능성 계산 결과를 보존합니다. 카드성 부채는 결제 계좌와
구조화된 다음 결제 금액·결제일을 가지며, 다음 수입 전에 결제할 금액은 필수 의무에도 연결합니다.

불규칙 소득, 가족 부양, 학자금·일반 부채를 지원합니다. 기존 할부, 리볼빙, 현금서비스,
카드론은 원금, 미지급 이자·수수료, 남은 회차, 금리, 최소 결제액, 다음 상환일, 연체 여부를
확인합니다. 모든 부채는 미지급 이자·수수료와 연체 여부를 명시합니다. 할부·리볼빙·현금서비스·
카드론은 금리, 전체·남은 회차, 최소 결제액을 적용 여부와 관계없이 보존하고 적용되지 않는 값은
`null`로 기록합니다. 다음 지급일은 `next_payment.due_at`만 사용합니다. 신규 사용을 권하지 않는
원칙과 이미 존재하는 의무 추적을 분리합니다.

## 제한 지원

다음 조건은 제한 지원으로 전환합니다.

- 지급일이 지났는데 의무가 미납인 경우
- 다음 수입 전에 지급할 필수 의무보다 정책상 사용 가능액이 적은 경우
- 사용자가 정한 횟수 이상 연속으로 현금흐름 적자가 발생한 경우
- 일반 예산 조정만으로 지급 불능을 해소할 수 없는 경우

채무조정, 회생·파산, 세무 신고, 개인사업 회계, 법률 판단이 필요하면 일반 흐름을 중단하고 전문
지원을 안내합니다. 스킬은 전문 판단을 대신하지 않습니다.

## 결산과 알림

결산 주기는 `every_event`, `daily`, `weekly`, `monthly` 중에서 선택합니다. 일반 거래는 선택한
주기에 모을 수 있지만 소득·고정비·부채 변화, 다음 결산 전 확정 의무, 지급 가능성을 바꾸는 사건은
즉시 입력해야 합니다.

직접 호출 모드는 실행할 때 밀린 결산을 먼저 확인합니다. 자동화 모드는 `period_id`마다 능동 알림을
최대 한 번 생성합니다. 미응답을 이유로 같은 `period_id`의 알림을 다시 보내지 않습니다. 다음
기간의 새 알림에는 과거 미결산 범위를 상태 정보로 요약할 수 있습니다.

## 사용자 경험

- 사용자는 "점심 12,000원 카드로 결제했어"처럼 일상어로 보고할 수 있어야 합니다.
- 내부 이벤트 이름과 회계 축을 그대로 질문하지 않습니다.
- 정보가 충분한 직접 입력은 바로 확정합니다.
- 계산 결과를 바꾸는 정보가 빠졌을 때만 한 번에 최소한으로 질문합니다.
- OCR, 알림, API 입력은 추출 결과와 중복 후보를 보여주고 사용자 확인을 받습니다.
- 현재 상태를 보여줄 때 기준일시와 마지막 결산 기간을 함께 표시합니다.

## 저장소 어댑터 계약

저장소 어댑터는 버전된 인계 데이터, 원본 이벤트, 알림 기록을 손실 없이 읽고 써야 합니다. 파생
상태는 원본 이벤트에서 다시 만들 수 있어야 합니다. 어댑터는 원본 이벤트를 조용히 덮어쓰거나
인증정보를 인계 데이터에 넣어서는 안 됩니다.

지원 저장소와 문서 배치는 별도로 선택합니다. 저장소가 정해지지 않아도 온보딩 결과를 표준 JSON으로
내보낼 수 있어야 합니다.

### Outline 어댑터

`outline-adapter.mjs`는 Outline 1.9.2 API에 자산관리 데이터를 저장합니다. 실행 환경에는 다음 값을
설정합니다.

| 환경 변수 | 값 |
| --- | --- |
| `OUTLINE_URL` | Outline 서버의 기준 URL |
| `OUTLINE_API_TOKEN` | 대상 collection에 문서를 읽고 쓸 수 있는 API token |
| `OUTLINE_COLLECTION_ID` | 자산관리 문서를 둘 collection UUID |

collection UUID는 설치 환경에 맞게 설정합니다. API token은 환경 변수나 secret store에서만
주입하며 문서, snapshot, 인계 데이터에 넣지 않습니다. 어댑터는
기본적으로 HTTPS URL만 받습니다. 운영자가 통제하는 개발망에서 HTTP가 필요하면 constructor에
`allowInsecureHttp: true`를 명시해야 합니다. API 요청은 redirect를 따라가지 않습니다.

어댑터는 collection의 기존 문서를 수정하지 않고 collection 직속 전용 root를 결정적 UUIDv4로
만듭니다. 문서 배치는 다음과 같습니다.

```text
자산관리 시스템
├── 이벤트
│   ├── 이벤트 인덱스
│   └── event_id별 불변 문서
├── 알림
│   ├── 알림 인덱스
│   └── period_id별 불변 문서
├── 인계 데이터
└── 파생 상태
```

인계 데이터와 파생 상태는 root 바로 아래의 고정 문서이며 전체 본문을 `replace` 방식으로 갱신합니다.
이벤트와 알림은 각각 `event_id`와 `period_id`로 문서 ID를 결정하며 생성 후 갱신하지 않습니다. 같은
이벤트 ID에 다른 내용이 있으면 충돌로 처리합니다. 같은 알림 기간을 다시 등록하면 최초 기록을
반환합니다.

이벤트와 알림 인덱스는 각각 해당 container의 mutable direct child입니다. 인덱스 데이터는
`index_version=1`과 `sequence`, `document_id`, 논리 key가 있는 entry 배열을 저장합니다. entry 배열의
순서가 append 순서이며, 이벤트와 알림은 이 순서로 반환합니다. `createdAt`과 `documents.list` 결과
순서는 replay 순서를 결정하지 않습니다.

각 문서 본문은 kind, version, 논리 key, data와 SHA-256 digest가 들어 있는 canonical JSON code
fence입니다. 어댑터는 문서 ID, collection, parent, 게시 상태와 envelope를 모두 검증합니다. 인덱스에
있는 각 문서는 `documents.info`로 다시 읽으며, 동시에 보내는 조회는 최대 4개입니다. container의
direct child는 100개 단위로 모두 나열한 뒤 인덱스 ID 집합과 대조합니다. 인덱스 문서나 불변 문서가
이동된 경우, 인덱스 entry에 있는 불변 문서가 없거나 이동·삭제된 경우, 인덱스에 없는 orphan이 있는
경우에는 읽기를 실패합니다. 삭제된 인덱스를 빈 문서로 다시 만들더라도 기존 child를 자동 편입하지
않습니다.

불변 문서를 먼저 만들고 인덱스 entry 갱신이 끝난 시점을 append commit으로 봅니다. 문서 생성 결과가
불명확하면 결정적 문서 ID를 다시 읽어 입력과 같은 문서인지 확인한 뒤 인덱스를 갱신합니다. 인덱스
갱신 결과가 불명확하면 현재 인덱스가 목표 상태인지 다시 읽어 확인합니다. 문서는 만들어졌지만 인덱스
갱신 전에 실패한 경우에는 일반 읽기가 orphan 오류를 반환합니다. 같은 이벤트 ID와 같은 내용을 다시
append하면 orphan을 검증한 뒤 다음 sequence로 인덱스에 편입하며, 다른 이벤트 내용은 충돌로
처리합니다. 알림은 같은 `period_id`를 다시 append하면 최초 orphan 문서를 인덱스에 편입합니다.

Outline 1.9.2의 문서 갱신 API에는 compare-and-swap 조건이 없습니다. 같은 collection에 쓰는 실행은
같은 JavaScript isolate에서 같은 module instance를 공유할 때 base URL과 collection ID를 기준으로
queue에 들어갑니다. 개별 public 메서드는 adapter instance가 달라도 순서대로 실행되지만, 여러 public
메서드로 구성된 read, replay, append, read, snapshot workflow 전체가 하나의 transaction이 되지는
않습니다. 다른 process, worker isolate, 중복 로드된 module instance의 reader와 writer는 이 queue를
공유하지 않습니다. 운영에서는 collection마다 writer process를 하나만 두고 다른 실행의 동시 접근을
피합니다.

어댑터는 HTTP 429를 자동으로 재시도하지 않습니다. 오류에는 HTTP status와 `Retry-After`, JSON으로
읽을 수 있는 응답 body가 보존됩니다. 호출자는 `Retry-After`가 지난 뒤 전체 public 메서드를 다시
호출합니다.
